## Findings as established

- Diff scope: three files, `requirements.txt`, `frontend/package.json`, `frontend/package-lock.json`. The lockfile's package set is identical to develop's (a JSON comparison of `packages` keys: none added, none removed). Nine entries change version: vite, vitest and seven `@vitest/*` packages. vite's dependency list is identical between 8.1.5 and 8.1.6.
- Install scripts: `npm view <pkg>@<ver> scripts` for all nine shows only `dev`, `build`, `lint`, `format`, `typecheck` style scripts, no `preinstall`, `install`, `postinstall` or `prepare`. No changed lockfile entry carries `hasInstallScript`.
- Publish times: vite 8.1.6 on 2026-10-06, vitest 4.1.12 on 2026-10-15, both over a week old.
- One oddity, upstream and harmless: vitest 4.1.12's own published `peerDependencies` lists `@vitest/browser-webdriverio` as `^4.1.11` while its siblings are pinned `4.1.12`. That is how the registry has it (`npm view vitest@4.1.12 peerDependencies`), it is an optional peer this project does not install.
- graphql-core 3.2.11 to 3.2.12 source diff (installed trees compared file by file): only `language/parser.py` (comment tokens now count toward `max_tokens`), `validation/rules/overlapping_fields_can_be_merged.py` (a 250,000 pairwise comparison budget) and `version.py` change.
- Wheel provenance: the scratch 3.2.12 wheel's sha256 `3d8f1045...1e51` matches the PyPI JSON record for `graphql_core-3.2.12-py3-none-any.whl`, uploaded 2026-08-27. The shared venv still holds 3.2.11 and was not touched.
- GraphQL tests under 3.2.12: `tests/system_03_search_agent/adapters/graphql`, 255 passed, 0 skipped, in 4.8 s. A pytest plugin of my own asserted `graphql.__version__ == "3.2.12"` at configure time and printed the parser module path at session end; both resolved to the scratch wheel, and the `src` imported was the worktree's.
- Limiter setup read: `security.py:164` `MAX_TOKEN_COUNT = 1000`, wired at `security.py:1029` as `MaxTokensLimiter(max_token_count=MAX_TOKEN_COUNT)`, which sets graphql-core's `parse_options["max_tokens"]`. The full ask document (every AskResult field) and the Integrations screen's printed GraphQL example (`frontend/src/components/screens/InfoScreens.tsx:146`) both parse under the limit.
- Comment padding probe, through the real `schema` with every extension: the full ask document with 10 leading comment lines and 2 inline comments reaches variable coercion ("Variable '$input' of required type 'AskInput!' was not provided."), so it passed the parser and every validation rule on 3.2.12, the same as on 3.2.11. On 3.2.12 the same document stays accepted with 960 comment lines and is first refused at 1000 ("Syntax Error: Document contains more than 1000 tokens. Parsing aborted."). On 3.2.11 even 1100 comment lines pass. So the probe discriminates the two versions, and only a document with roughly 950 or more comment lines is newly refused. No legitimate client sends that; the refusal is the existing disclosable syntax error message, not a masked one.
- Comparison budget probe: `query { run(runId: "x") { answer x N } }` for N of 100, 700 and 990 gives identical results and timings on 3.2.11 and 3.2.12 (990 refused by the token limit first). The 1000 token limit keeps any document far below 250,000 field comparisons in this shape, so the new budget does not change what our surface accepts. If it ever fired, its message is not in the disclosable allowlist and would show as the generic internal error, a cosmetic point and not worse than develop, where such a document would simply spend CPU.
- Frontend installed versions: `node_modules` holds vite 8.1.6, vitest 4.1.12 and all seven `@vitest/*` at 4.1.12 (read from each package.json); `npx vitest --version` prints 4.1.12.
- `npx vitest run`, four runs on a machine with load average 31 to 66 on 8 cores (other overnight work running): default workers gave 29 failed then 8 failed; three workers gave 2 failed then 0 failed, 670 of 670 passed. Every failure was vitest's per-test timeout (`STACK_TRACE_ERROR` from `@vitest/runner` `withTimeout`), the failing set changed run to run, and the four worst files (`App.depthToggle`, `App.historyAfterStop`, `App.historyNoAnswer`, `App.test`) passed 56 of 56 alone with two workers. I read this as load starvation, not the bump, but I did not run develop's 4.1.11 under the same load to compare, so that part is inference. CI's gate is the cleaner signal.
- `npm run build` (`tsc -b && vite build`): passes on vite 8.1.6, 948 modules, built in 0.5 s. It prints the large chunk warning for the 610 kB main bundle, a warning and not a failure.
- Gate 10's spec, `npx playwright test e2e/accessibility.spec.ts`: 10 of 10 passed in 26.7 s. I confirmed ports 5273 and 8931 were free first and ran with `CI=1`, so Playwright started fresh servers rather than reusing someone else's: the vite 8.1.6 dev server from the worktree and the mock backend importing the worktree's `src` (its log paths show `s3-worktrees/deps/src`). So the dev server starts and serves the app on the bumped vite.

Both are app level, not vite level. I did not compare them against develop.

The same `npm audit --audit-level=high` against develop's `package.json` and lockfile (copied to a scratch folder, `--package-lock-only`) reports 3 vulnerabilities, 1 high (vite 8.0.0 to 8.1.5) and 2 moderate (vitest and `@vitest/mocker` up to 4.1.11). The shared venv still reports graphql-core 3.2.11 after the run.
- No other file in the repository pins graphql-core, vite or vitest to the old versions (`git grep`, outside history documents). The commit uses the GitHub noreply address and carries no co-author trailer.

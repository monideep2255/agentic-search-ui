## Findings

### A-139-01: When one kind's summary call fails, the note says "this answer shows 0" and the only failure note does not say which records failed
- Severity: minor (a different cause from the judge's J-139-02: here the zero is a failed call, not an absent kind; the new count is true, so this is not worse than develop's "shows 10")
- What: `core/graph.py:10103` to `10108` passes `_paper_link_shown(...)`, which counts only the summary call's returned records. When the ESummary call for a kind errors, the link search still reports `ok` with NCBI's total, so the note reads as if the answer chose to show none. The failed-call note that accompanies it names no database ("The background search of NCBI records did not finish"), so nothing tells the reader the zero is a failure and that asking again may fill it.
- Reproduction: my probe (scratchpad `p/test_adv139.py`, real `plan_node`, `act_node`, `write_node`, NCBI stubbed with realistic ESummary fields per kind, Act's whole returned state passed into Write), `PICK=sequences`, links nuccore 20 of 1533 and assembly 8, the nuccore ESummary returning `status="error"`. Notes, in order: "NCBI lists 1533 sequence records linked to PMID 11237011; this answer shows 0." / "NCBI lists no linked SRA run records for PMID 11237011." / "NCBI lists 8 genome assemblies linked to PMID 11237011; this answer shows 5." / "Note: no written summary could be checked against the records, so this answer lists the records found with their sources" / "The background search of NCBI records did not finish, so this answer may be missing sources from it. Ask again to retry."
- Why it matters: a researcher reads "NCBI lists 1533; this answer shows 0" as the product deciding not to show sequences, when the call failed. "A refusal says what to type next": the count note is the place that could say the sequence lookup failed.
- NOT FIXED

### A-139-03: The new fallback wording says "this answer lists the records found" over an answer that drops one, and the web screen hides the only note that says so
- Severity: minor (the claim predates this card in its "listed below" form, but this card rewrote this exact sentence to make it true and left this half of it false; the count note beside it is correct)
- What: `_build_structured_fallback_note` (`core/graph.py:10996` to `10999`) says "so this answer lists the records found with their sources" whenever the structured fallback fires. When the code-built listing itself fails to ground one record, the answer lists fewer records than were found, and `_build_incomplete_answer_note` adds "Note: one further nuccore record was found for this question and is not included in the list above". `frontend/src/components/screens/AnswerScreen.tsx:648` (`/^Note: (?:one|\d+) further /`, filtered at line 1888) hides that note on screen, so the reader sees only the claim that the found records are listed.
- Reproduction: my probe, `PICK=sequences`, nuccore 20 of 1533, writer replying "ok", one ESummary record (`nuccore/1012`) with `title="[3]"`. Output: `ROWS 4`, `CITES 4`; notes "NCBI lists 1533 sequence records linked to PMID 11237011; this answer shows 4." / ... / "Note: no written summary could be checked against the records, so this answer lists the records found with their sources" / "Note: one further nuccore record was found for this question and is not included in the list above". The last note matches the web hide pattern; the fallback note does not.
- Why it matters: "Honesty beats polish" was the card's rule. On the web, the sentence the card made "true" still tells the reader every record found is listed when one is not, and nothing visible says otherwise. A narrower wording ("lists the records it could check") would be true on both paths.

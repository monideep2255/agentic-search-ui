### The manual smoke test

- Before running any query, checked whether the live knowledge graph was actually reachable from this session, since past tracker entries had flagged this as a known constraint. A direct TCP probe to the tunnel's expected local port came back refused.
- Product owner pushed back directly: "why is the graph not reachable? it should work." Answered precisely rather than deflecting: the graph server itself is healthy and reachable in general, over SSH, but this specific coding session runs inside a sandbox whose only outbound network path is an HTTPS proxy, which cannot carry raw SSH traffic, a protocol-level limitation, not a bug in the product. Cited the repo's own decision log (2026-07-29, 2026-08-05) confirming this was already a known, documented constraint, not a new discovery.
- Product owner asked the sharper follow-up: "then how have you been checking the queries?" Answered honestly rather than assert confidence: this specific session had never run a live graph query at any point, every "9 of 9 live" figure cited earlier in the conversation came from reading tracker files recording results from earlier sessions, not from anything independently re-verified today. Also stated plainly what was NOT known: which environment those earlier sessions actually ran in.
- Product owner asked how to set up tunnel access. Pulled the exact, historically-verified command from the decision log rather than reconstruct one from memory (`ssh -N -L 15432:127.0.0.1:5432 root@46.225.128.133`), and explained why it has to run in the product owner's own terminal: the coding session's own Bash tool is blocked from invoking `ssh` at all, by a dedicated safety hook, independent of the network-layer restriction.
- Product owner asked the most important question of the exchange: "so you cannot run the tunnel on my behalf? how will it run for the UI stage then?" Answered in full: the SSH tunnel was never meant to be the production path, it's a deliberate, zero-build prototype shortcut (Decision D, "transport-per-phase"). The real plan for when this ships is a small, always-on HTTPS service co-located on the same Hetzner box as the database, talking to Postgres over localhost with no network hop, reached by the deployed backend over a plain HTTPS call exactly like any other API call already made. That service is a named build target (Section 24) and has not been started. Made clear that right now, nobody, not this session, not a deployed server, can reach the graph the production way, which is expected at this stage, not a gap specific to today.
- Product owner's resolution: "ok, we will build it later then. do the testing as needed then," authorizing the Layer-2-only smoke test to proceed now rather than wait.

# Phase 3.4: citation trust extended to Layers 2 and 3

Build phase 3.4 delivers provenance extended to Layer 2 and 3 (the four added `CitationPayload` fields: `evidence_kind`, `assertion_confidence`, `population_ancestry_context`, `license`), the two-tier risk gate (standard cite-or-refuse versus the higher-stakes substantiation-and-triangulation gate) made reachable across layers, and data freshness and conflict resolution (Section 7). This is the last prerequisite phase before the delivery-surface and observability build phases (4.0 onward): four downstream phases (4.1, 4.6, 4.7, 5.1) wait on it.

Depends on: build phases 2.2, 3.1, 3.2, 3.3, 3.5, all done.
Branch: `phase/3.4-citation-trust-full`
Spec: `requirements/Technical_specification.md` Section 9 (provenance and the four added fields), Section 7 (layer authority, freshness, conflict resolution), Section 8 (grounding and the two-tier risk gate), Section 25's own line for this phase
Reference: `tracker/phase_3.5.md`'s transferable lesson (fix-regression-one-layer-downstream), `LEARNINGS.md`'s trust/provenance/grounding entries and the 2026-08-08 rows, `docs/build/Build_velocity_post_mortem.md`

## Scope decision: T-3.1-28 folded in

Confirmed with the product owner 2026-08-09, logged in `DECISIONS.md`. T-3.1-28 (wire the Act step to dispatch a Layer 2 tool as an answer-bearing tool alongside `cypher_query`, with a Layer 2 citation payload and trust gate) has been carried past every tool phase (3.1 through 3.5) as an unscheduled, separately-tracked ticket. Section 25's literal line for 3.4 does not name it. But `synthesis/trust.py`'s own module docstring states the two-tier risk gate's concordant/discordant triangulation paths become reachable "with no change to this module beyond the origin table" once a Layer 2/3 tool supplies a relationship type at Act time, and build phase 3.4 is the one phase whose entire subject is that trust mechanism. Building the machinery without wiring a second origin would leave triangulation provably untestable end to end, so T-3.1-28 is folded into this phase (ticket T-3.4-05) rather than left further deferred.

## Phase premise (the done-when)

A query whose answer is expressible from both Layer 1 (the graph) and a live Layer 2 call for the same entity (the pinned example: BRCA1's gene record, resolvable both via `cypher_query` and via `ncbi_efetch`) dispatches both tools from Act, and the citations in the final answer carry full Section 9.1/9.2 provenance for both layers, not just Layer 1: real `evidence_kind`, `assertion_confidence`, `license`, and `population_ancestry_context` (or an honest `null`) on every citation, never a placeholder or an `unspecified` license. The flagship gene-disease claim ("which diseases are associated with BRCA1?") is classified `high` risk via the traversed `gene_associated_with_condition` edge label, not the `Disease` endpoint's bare node type, and triangulates against Layer 2/3 evidence with a real `concordant`/`discordant`/`insufficient` verdict, never staying stuck at `not evaluated` because no second origin exists to compare. A genuine conflict between a graph value and a live value for the same field is detected by code, never a free-text diff, and produces a `flag` trust outcome citing both sources, never a silent pick of one side. A Layer 1 field past its staleness threshold (30 days volatile, 90 days stable, Section 7.4) auto-cross-verifies against a live Layer 2 call before being cited as current. A citation for a coordinate or sequence claim carries an explicit `assembly` field, refused with `assembly: null` when unresolvable, never silently omitted.

Per `tracker/phase_3.5.md`'s transferable lesson, quoted: "a fix for a discard-real-data defect is exactly the kind of change most likely to reintroduce the identical defect one layer over... Only live re-verification against the adversary's own repro case, re-run after every round of changes, caught both regressions here; a fully green mocked test suite caught neither." This phase IS the trust/provenance mechanism, so every ticket touching the risk gate, freshness, or conflict path gets live re-verification after every fix round, not just the mocked suite.

The verify surface is `tests/system_03_search_agent/synthesis/test_citation_trust_full_premise.py`, not a suite total, per `tracker/phase_3.1.md`'s standing rule.

## What already exists (from the research brief, confirms less new work than Section 25's line implies)

- `CitationPayload` (`contracts/events.py:118-134`) already carries all four Section 9.2 fields in the wire schema. No schema change needed there.
- `TrustSignalPayload` (`contracts/events.py:137-`) already models the full Section 8.3.3 decision table's output shape: `outcome`, `risk_tier`, `grounded`, `triangulated` (tri-state), `citation_id`, `scope`.
- `write_node` (`core/graph.py:2557-`) already emits per-claim and answer-level `trust_signal` events, already calls `trust_for_claims`/`aggregate` from `synthesis/trust.py`, already has a working refuse path (Section 8.4) with a host-pinned fallback link. The two-tier decision table itself is wired, for the Layer-1-only case.
- `synthesis/trust.py` already implements `risk_tier_for`, `triangulate`, `_origin_of`. Six of seven high-risk relationship tokens are dead code today, pre-wired for the moment a Layer 2/3 tool supplies one.
- `synthesis/grounding.py`'s Section 8.2 matching rule is layer-agnostic already; no changes needed for this phase.

What is genuinely missing: per-tool provenance defaults and citation-building for all six Layer 2/3 tools (currently `source_url`-only), the F-2.2-A-05 edge-label fix, Act-step dispatch of a second layer (T-3.1-28), and all of Section 7 (freshness, staleness, conflict detection), none of which exists in any form yet.

# Build phase 4.6: feedback capture

Branch: `phase/4.6-feedback-capture`
Spec: `requirements/Technical_specification.md` Section 15 (the `interactions`, `sessions` and `cq_candidates` tables), Section 16 (the five-stage feedback loop, v1 scope stages 1, 3 and 5), Section 17 (the few-shot example and eval case payloads), Section 11.3 (PII handling), Section 25 (row 4.6)
Depends on: 1.1 (PR #6) and 3.4 (PR #28), both verified merged at phase open
Opened: 2026-08-21

## What this phase delivers

Section 25's line: real interaction capture into `interactions` (query, route, rubric outcome, citations, coverage tags, feedback, `trace_id`), the manual review ritual, and hand-promotion into few-shot examples.

Section 16 scopes the loop for v1 to three of its five stages. Stage 1 is capture, stage 3 is the human-gated weekly review, stage 5 is few-shot promotion. Stage 2, the automated mine-and-cluster job, is named out of scope by the PRD and by `.claude/rules/v1-scope-boundary.md`, and stage 4's trigger rule runs inside the same manual review rather than as its own pass. This phase does not build a clustering job, and a builder who finds one easy is crossing the v1 boundary.

## The goal contract

Written before any ticket, per `.claude/rules/goal-contracts.md`.

- Done when: every completed query, on every callable surface and at every one of the four trust outcomes, writes exactly one `interactions` row attributed to the right principal; a caller can attach feedback to their own row and to nobody else's; the weekly review ritual and the promotion path run as real scripts against real rows; and the two daily caps that have read an always-empty table since build phase 2.0 actually fire.
- Verify: this phase's premise gate run live with `RUN_PREMISE_GATE=1`, every arm mutation-proven; the Python suite against a re-measured baseline, never a carried-forward one; `ruff check` on every file touched; `python tracker/check_doc_drift.py --check`; and a second, independent judge and adversary round before merge.
- Output: the branch `phase/4.6-feedback-capture` and one pull request.
- Constraints: capture never blocks, slows, or fails a query whose answer already streamed. No column of `interactions` ever holds a secret THIS SYSTEM HOLDS: no API key, token, credential or connection string from the configuration or the harness. CORRECTED 2026-08-21 by F-4.6-A-12, and the original wording is kept here rather than replaced because the way it was wrong is the useful part. It read "No column of `interactions` ever holds a secret", full stop, which is FALSE and cannot be made true: a user who pastes a credential into the question they are asking about it has that string stored verbatim, and Section 16 requires `query_text` be captured or the review ritual cannot function at all. The premise gate's P10 arm tests the narrowed version, which is the one it could actually enforce, by planting a secret in the environment and grepping every column for it. Whether the storage path should grow a redactor for user-pasted credentials is a product decision and is filed as F-4.6-A-12, not settled here. Ownership keys on `Query.owner_id`, never on `user_id`. `interactions.session_id` uses `core/session_memory.session_row_key`, never a second mapping. Every gate in `production-standards` holds.
- Blocked-stop: a change to any cost-cap threshold value, which `system-design-patterns` pattern 4 reserves to the product owner. Capture makes the caps live for the first time; it does not retune them.

## What the code actually looks like at open, measured rather than assumed

Six facts found by reading the source before decomposing. Each one moves a ticket, and two of them contradict what a reading of the specification alone would suggest.

- The schema already exists and needs no migration. `data/models.py` carries `Interaction`, `CqCandidate`, `ChatSession` and `SavedQuery` in full, with every check constraint and every index Section 15 names, shipped at build phase 1.1 by alembic `0001_user_data_schema`. This phase writes rows; it does not create tables.
- NOTHING IN `src/` WRITES AN `Interaction` ROW. That is F-2.0-04 stated as a fact rather than a flag: `get_user_daily_query_count` and `get_system_daily_cost_usd` (`harness/cost_control.py:436` and `:515`) both query live and both always return zero, so the per-user and system-wide daily caps cannot fire in production and have not since build phase 2.0.
- `Query.trace_id` is client-supplied and never server-overwritten (F-2.0-10). Section 20.1 says it is minted at Guardrail. Because `interactions.trace_id` is `UNIQUE` and the insert is `ON CONFLICT (trace_id) DO NOTHING`, a client that reuses one `trace_id` writes at most one row per day and evades the 100-query cap entirely. The cap and the mint are one ticket, not two, which is why F-2.0-10 was boarded here alongside F-2.0-04 rather than fixed in isolation.
- `sessions` rows are created lazily by session memory, not at session start. `_PostgresSessionMemoryStore.update` inserts a `ChatSession` on the first turn that has anything to remember. So `interactions.session_id`, a foreign key to `sessions.id`, can point at a row that does not exist yet on a turn that resolved no entity and grounded no finding. Capture must create or tolerate that row itself rather than assuming memory made one.
- `coverage_tags` has a real source and it is not the event stream. `synthesis/trust.py` already reads traversed edge labels off the generated Cypher through `cypher_query._traversed_edge_type_by_column`, and pairs each citation with a `node_or_edge_type`. That pair is what `concept:<Label>` and `predicate:<edge_type>` are derived from. A builder reaching for `ToolResultPayload` will find `summary`, `result_count` and `truncated` and no labels at all.
- `query_class` is still the build-phase-2.0 stub. `think_node` hardcodes `"lookup"` for every query (F-2.0-15, assigned to build phase 4.7). So `interactions.query_class` will read `lookup` on every row this phase writes. That is correct behaviour for this phase and a known-wrong value in the data, and it must be recorded as such rather than worked around here.

## The trap this phase can most easily ship

Two, and both are silent.

The first is attribution. Build phase 4.5's review round found that every guest shared one ownership identity, because `user_id` is NULL for a caller with no account. Capture writes `user_id` and `session_id` on every row. If either is keyed off `user_id`, every guest's interactions land in one bucket, every guest's feedback overwrites every other guest's, and the review ritual reads a merged conversation as one user's pattern. The distinguishing identity is `Query.owner_id`, the namespaced principal, and `session_row_key(session_id, owner_id=...)` is the only mapping permitted to produce `interactions.session_id`.

The second is the gate supplying the thing under test. Build phase 4.5's F-4.5-09 shipped a memory feature that never wrote a summary, while eight gate arms passed, because every arm handed the memory in on `RequestContext`. The identical shape is available here: a gate that constructs an `interactions` row and asserts the assembler shaped it correctly proves nothing about whether a real query ever causes one to be written. At least one arm must run a real query end to end and then look in the database for a row nobody put there.

## Scope seam with build phase 4.7

Section 17 places the few-shot pool in a versioned file loaded once at process start, and build phase 4.7 owns the routing that consumes it. This phase owns the promotion path that WRITES to it. So 4.6 creates the pool file and the golden-dataset file and appends to them; it does not wire the orchestrator to read either. A promoted example that no orchestrator reads yet is the correct end state for this phase, and 4.7 picks it up.

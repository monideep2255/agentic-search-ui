## What this phase is for

Today there is one deployment. Build phase 4.12 wired CD to `develop`, so every merge to `develop` reaches the public URL that has been handed to people. There is no place to see a change running before the audience sees it, and build phase 4.14 made CI advisory rather than merge-blocking (F-4.14-A-04), so nothing structural stands between a merge and the demo.

The deliverable is two environments with separate URLs, separate variable sets and separate data, and a branch flow that promotes code from one to the other deliberately rather than on every merge.

Measured on `phase/4.15-release-environments` at its branch point, `9b4d1ad`, on 2026-08-27. This table is the input to the design rather than a summary of it, following build phase 4.14's practice, and two of its rows changed what the tickets say.

Two measurements changed the plan.

The CI trigger is HALF DONE ALREADY, and the half that is missing is not the half it looks like. `on: pull_request:` carries no branch filter, so a pull request targeting `main` already runs all ten gates today. Only the `push` trigger names `develop` exclusively, so what is missing is the post-merge run on `main`, not the pre-merge one. Writing the ticket from the assumption instead of the measurement would have added a redundant `pull_request` filter and left the real gap open.

`railway environment new --duplicate` decides HOW the second environment is built, and the reason is build phase 4.12's most expensive learning. `search-agent-web`'s Root Directory is a dashboard-only field: that phase deployed a second copy of the Python API into the static frontend service, and could not fix it from the CLI at all. Creating the develop services from scratch would mean setting that field again by hand. Duplicating carries it. So this phase duplicates and then OVERWRITES the variables that must differ, rather than building the environment up from nothing.

### A gap found while measuring, not predicted

`env.example` and the deployed service disagree in both directions, and one direction is a live defect.

| In `env.example`, NOT set on any service | Set on a service, NOT in `env.example` |
|---|---|
| `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` (alternate providers, unused) | `RUN_MIGRATIONS_ON_STARTUP` |
| `GRAPH_PG_HOST/PORT/USER/PASSWORD/DBNAME` (superseded by `GRAPH_QUERY_URL` at build phase 4.11) | `NIXPACKS_NO_CACHE` |
| `LANGSMITH_API_KEY`, `POSTHOG_API_KEY` (build phases 5.0 and 5.1, unbuilt) | `NIXPACKS_NODE_VERSION` |
| `OPERATOR_USER_IDS` (optional), `PORT` (Railway auto-sets it) | |

The left column is all explainable. The right column is not, and `RUN_MIGRATIONS_ON_STARTUP` is the one that matters: it gates `alembic upgrade head`, which `railway.json` runs as the first half of the start command, and it is absent from the file this repository tells people to provision from. Build phase 4.14 recorded that "about thirty environment values the suite needs" were missing from a clean machine and fixed it by DIFFING `env.example` against the job rather than discovering them one failure at a time. This is the same defect one layer out: provisioning a second environment from `env.example` alone would silently omit the variable that decides whether migrations run. Filed as F-4.15-01 and closed by T-4.15-06.

## What the refinement settled

Settled 2026-08-27 and logged in `DECISIONS.md`. The board row carried these as open questions since 2026-08-24.

| Question | Answer | Who decided |
|---|---|---|
| Separate environment or separate project | A second environment in the existing project | Section 24, which already names the feature |
| Which environment keeps the live URL | The existing one stays production and keeps `search-agent-web-production.up.railway.app` | Lead, on the ground that the URL is already in circulation |
| Shared or separate Postgres and Redis | Separate. Develop gets its own | PRODUCT OWNER, 2026-08-27 |
| `AUTH_SECRET` | Generated per environment, never shared | Section 24 |
| `CORS_ORIGINS` | Per environment, naming that environment's own web URL | Section 24 plus the URLs |

The data split was the only part that spends money and the only part that was genuinely open. It was decided against sharing on two grounds this build has already measured rather than on principle: build phases 4.6 and 4.10 count `interactions` rows to enforce the daily caps, so shared data would spend production quota on test traffic and pollute what build phase 4.13's history rail renders; and `railway.json` starts with `alembic upgrade head`, so a shared database carries a wrong migration into production the moment it merges to develop, which is the same unguarded promotion build phase 4.14 exists to stop, one layer down.

## Goal contract

Written before the first change, per `.claude/rules/goal-contracts.md`.

Done when, all five. REWRITTEN 2026-08-27 after finding F-4.15-J-02: the original text was written before two mid-phase redesigns and three of its five items had become literally false, which made the contract useless as a verify surface at exactly the moment it was needed. The original wording is not preserved here because `requirements/Plan.md` and this file's History section already carry the narrative; what a contract must be is TRUE.

1. Two deployments exist, `production` in Railway project `system3-search-agent` and `develop` in `system3-search-agent-develop`. Each has its OWN Postgres, Redis and `AUTH_SECRET`, and its own api and web services answering at distinct public hostnames. TWO PROJECTS rather than two environments, per F-4.15-03.
2. The develop project watches the `develop` branch and the production project watches the `production` branch.
3. `production` exists on origin, `develop` remains the DEFAULT branch, and CI runs on a push to either as well as on a pull request into either.
4. The release flow is written down in one document that is the source of truth for how a change reaches production, including the release branch, the tag, the changelog and the back-merge.
5. Every arm of the premise gate that CAN pass today does, every arm is proven able to fail by a mutation harness, and any arm that cannot yet pass says so with its unblocking condition named.

Item 5 is stated that way deliberately rather than as "every arm passes", and the reason is finding F-4.15-A-09. P5 compares the `app_env` field that this phase ADDS to `GET /health`. Neither deployment can report it until the code reaches it, and they get it at different times: develop when this pull request merges, production only when the first release is cut. MEASURED 2026-08-27, both return `{"status":"ok"}` with no `app_env`. A contract that demanded P5 green before merge would be demanding something the merge itself is a prerequisite for, so it would be met only by weakening the arm, which `goal-contracts` forbids. P5's unblocking condition is named here and repeated in the phase's open items.

Constraints, true throughout:

- No secret value is ever printed, logged, or written to a tracked file. Variable NAMES are read and compared; values are never rendered. Where a value must be compared, it is compared by behaviour, not by content.
- `production` keeps its name, its public URL and its data. Nothing in this phase migrates, drops or rewrites production data.
- Production is never left watching a branch that does not exist. `main` is created and pushed BEFORE production's trigger moves to it.
- No merge to `develop` during the window between creating the develop environment and pointing it at the branch.

Blocked-stop, any of:

- Railway refuses a second environment on the current plan. Report the plan requirement and its cost; do not work around it by reusing production.
- The duplicate carries production's database credentials as literals rather than resolving `postgres.railway.internal` per environment, so develop would read production data. Stop before starting any develop service.
- Repointing production's trigger would leave the live URL serving nothing.

## Coverage: what this phase does not cover

Stated in the phase file rather than left to be discovered, per `.claude/rules/goal-contracts.md`, "a verify surface must state its own coverage".

- The gate does NOT prove that a release cut from `develop` and merged to `main` actually reaches production. It proves the triggers are configured and that a deploy happened. The first real release is the proof, and it is out of this phase.
- The gate does NOT test rollback. Railway's rollback is redeploying a previous build from its history, which is a console action with no API surface exercised here.
- The gate does NOT prove the two Postgres instances hold different DATA at rest. P2 proves it through the auth path, which is the path that matters, and says nothing about the `interactions` or `runs` tables.
- The gate does NOT make CI merge-blocking on `main`. F-4.14-A-04 is unchanged by this phase: branch protection still needs GitHub Pro or a public repository, so a red check on a release pull request still sits beside a working Merge button. This phase adds a second place that is true rather than fixing it.
- P6 compares variable NAMES, never values. A variable present in both environments with production's value copied into develop passes P6. P3 and P4 cover the two cases where that would actually be dangerous; nothing covers the rest.
- P3a creates a real account on BOTH deployments on every run and nothing tears them down, so the production user table grows by one row per gate run, unbounded (finding F-4.15-A-16). Accepted rather than fixed, and the reasoning is recorded because the alternatives are worse: a fixed reusable gate account means a checked-in credential, and a teardown path means giving the gate delete rights against production, which is a larger hazard than a few marked rows. The rows are identifiable, `gate-4.15-<uuid>@example.invalid`, and P2 writes only to develop. If this ever needs fixing, the right shape is a signature probe that does not require an account at all, not a delete path.
- Nothing here tests the graph credential per environment. Both environments point at the same read-only HTTPS graph query service, deliberately: Layer 1 is read-only at the connection level, so there is no develop-versus-production hazard to separate.
